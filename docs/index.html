Mini Workflow Engine · Working notes

How this engine works, and what's left

A single reference for the concept, the four-part reading path through the code, the current gaps and how to close them, and the questions that shaped this design.

01 The core idea

The engine does not invent a workflow or decide that a process needs another step. The person or application setting up a process supplies the states and transitions. The backend stores those rules, then applies them when actions arrive.

The codebase splits that job into five layers, each with one responsibility:

LayerJob
ControllerReceives an HTTP request and reads its URL, headers, and JSON body.
DTOsDefine the shape of that JSON input and output.
ServiceApplies the rules: create an instance, find an allowed transition, update the state.
Model / entityRepresents definitions, states, transitions, instances, and related records in Java.
RepositoryReads and saves those records in the database.

In WorkflowEngineController, this call is the hinge point of the whole system:

workflowInstanceService.executeAction(
  instanceId,
  request.getAction(),
  ownerId,
  request.getData(),
  callerRole
);

The controller has received an action from another application. It hands that action to the service, which answers the real question: given this instance's current state, is there a transition for this action? If so, the instance moves to that transition's destination state.

The engine knows nothing about your business. It doesn't know what "recruiter," "admin," or "approved" mean. Those are rules the integrating application supplies as a workflow definition. A future visual workflow builder would just be a frontend that lets a person draw states and arrows, then sends the resulting definition to this same backend.

02 The request lifecycle

One workflow is set up once. Every subsequent action re-enters the same loop: check, move, record.

The dashed box is the only place a decision gets made: WorkflowEngineService looks up whether a transition exists from the instance's current state for the given action. Everything above it in the diagram happens once; everything below the "send an action" box repeats for every action executed on that instance.

03 A real deployment

Using a recruiter-approval process as the example, hosted inside an application called GIU Nexus.

Defining the workflow

Someone defines the process before any recruiter is reviewed:

States:  PENDING → LEVEL_1_APPROVED → LEVEL_2_APPROVED → APPROVED
Actions: approve_1, approve_2, approve_3

That definition is sent to POST /workflows as JSON. The backend validates it and saves it. Later, one instance is created per recruiter being reviewed.

Running it

  1. A head admin sets up the recruiter approval workflow once.
  2. When a recruiter signs up, GIU Nexus creates a workflow instance for that recruiter.
  3. An admin clicks Approve inside GIU Nexus.
  4. GIU Nexus sends an action to the workflow engine.
  5. The engine checks the current state and the allowed transition, saves the new state, and returns it.
  6. GIU Nexus displays the updated approval status.

GIU Nexus owns the screen and the business experience. The workflow engine owns state progression and its rules — nothing more.

04 Why use an engine at all

It earns its keep once several processes need the same machinery. Job applications, recruiter approvals, leave requests, and support tickets all have different states, but they all ask the same four questions:

  • What state is this item in?
  • Which action is allowed next?
  • Who is allowed to perform it?
  • What happened previously?

Instead of writing a separate set of state-changing code for every process, an application defines each process once and lets the engine manage its progression.

One practical caution, straight from the controller code: X-Owner-Id and X-Caller-Role are values supplied in request headers. A real deployment needs a trusted way to establish identity and role before those values can be used for access control — see Known limitations below.

In one sentence: an application defines the route, and the engine tracks each item as it moves along that route.

05 The reading path

The 34 source files don't need to be read top to bottom. They read best in four phases, each following one request through the whole stack — input DTO, controller, service, model, repository.

1
How a workflow is defined
CreateWorkflowRequest → StateRequest & TransitionRequest → WorkflowController → WorkflowService → WorkflowDefinition, State, Transition → their repositories
CreateWorkflowRequest dto

Receives the JSON for the whole new workflow: its name, version, states, and transitions. It carries the input — it doesn't save anything itself.

StateRequest dto

Receives the details for one state in that JSON: its name, and whether it's the starting state.

TransitionRequest dto

Receives the details for one allowed move: the action, the state it starts from, the state it goes to, and optionally a guard condition or a required role.

WorkflowController controller

Receives the POST /workflows request. Takes the CreateWorkflowRequest, passes it to WorkflowService, and returns the result as JSON.

WorkflowService service

Does the creation work: checks every state and transition (exactly one initial state, no duplicate names, every transition's states exist, guard fields are all-or-nothing), then builds and saves the records.

WorkflowDefinition model

The saved workflow template. Represents the workflow as a whole, scoped to an owner, holding its list of states and transitions.

State model

A saved state belonging to that workflow definition, with a flag marking whether it's the entry point.

Transition model

A saved rule connecting two states through an action, with optional guard fields and an optional required role.

WorkflowDefinitionRepository, StateRepository, TransitionRepository repository

Provide the database operations used to save and look up those records — including owner-scoped lookups so one integrator can't read another's workflow.

2
How an instance runs
CreateWorkflowInstanceRequest / ExecuteActionRequest → WorkflowEngineController → WorkflowInstanceService → WorkflowEngineService → WorkflowInstance → WorkflowInstanceRepository
CreateWorkflowInstanceRequest dto

Holds the JSON needed to start one instance: which workflow definition to use, an optional external reference ID, and optional initial data.

ExecuteActionRequest dto

Holds the action name and any data sent when someone tries to move an instance to another state.

WorkflowEngineController controller

Receives every /workflow-instances request: create, execute, read by ID, read by reference, history, and events. Translates HTTP into service calls and back into JSON — no business logic of its own.

WorkflowInstanceService service

Owns the life of an instance: finds the workflow and its initial state to create one, saves incoming data before evaluating a transition, asks WorkflowEngineService for the next state, then saves the new state, a history entry, and a transition event.

WorkflowEngineService service

The actual state-machine decision. Looks up every transition starting at the current state matching the action, picks the first whose guard holds, checks the required role, and returns the destination state — or throws if nothing matches.

WorkflowInstance model

Represents one real item going through a workflow: which definition it follows, which state it's currently in, its owner, and its external reference ID.

WorkflowInstanceRepository repository

Reads and saves instances, scoped by owner ID and lookup by external reference, so one integrator can never read or execute another's instance by guessing an ID.

3
Guards and role checks
GuardOperator → InstanceVariable → GuardEvaluator → Transition.requiredRole → ForbiddenActionException → GlobalExceptionHandler
GuardOperator model

A fixed set of comparisons a guard can use: EQUALS, NOT_EQUALS, GREATER_THAN, LESS_THAN, and their "or equal" variants. Kept as a closed enum, never free-text, so a guard can never execute arbitrary code.

InstanceVariable model

One key/value pair of business data attached to an instance, e.g. score = "85". Always stored as text; comparisons decide at evaluation time whether to treat it as a number.

InstanceVariableRepository repository

Reads every variable for an instance, and finds one by name so saving data updates the existing row instead of duplicating it.

GuardEvaluator service

Decides whether a transition's guard holds. An unguarded transition always matches. A guard whose variable is missing on the instance is treated as not matching, not as an error. Numeric values compare numerically; non-numeric values only support equals/not-equals.

Transition.requiredRole model

An optional field on a transition. When set, only a caller declaring that exact role via X-Caller-Role may execute it. A missing header is treated as "no role," not as "check skipped."

ForbiddenActionException service

Thrown when a caller has the right owner ID but the wrong role for a specific transition — kept distinct from a malformed-request error so it maps to HTTP 403, not 400.

GlobalExceptionHandler controller

Catches exceptions thrown anywhere in the app and turns them into a structured JSON error response with the right HTTP status, instead of a generic server error.

4
History and the event feed
TransitionHistoryEntry / TransitionEvent → their repositories → WorkflowEngineController (history, events) → response DTOs
TransitionHistoryEntry model

Records one executed transition on one instance — action, from-state, to-state, timestamp — as a permanent audit trail, stored as plain name strings so it stays readable even if the workflow definition later changes.

TransitionHistoryEntryRepository repository

Returns an instance's full history in the order it happened, oldest first.

TransitionEvent model

A system-wide record of a transition, scoped by owner rather than linked by relation, with a dispatched flag a future webhook worker could flip once it has actually notified someone. Nothing flips it today.

TransitionEventRepository repository

Returns every event for an owner across all of that owner's instances, oldest first — the activity feed a future dispatcher would poll.

TransitionHistoryEntryResponse, TransitionEventResponse dto

Define the JSON shape returned by GET /workflow-instances/{id}/history and GET /events.

WorkflowDefinitionResponse, WorkflowInstanceResponse, ErrorResponse dto

The remaining response shapes: a workflow's full states and transitions, an instance's current state and data, and the structured error body used by GlobalExceptionHandler.

TestDataConfig config

Seeds a demo "Job Application" workflow on startup, so there's something to call the API against without creating a workflow by hand first.

MiniWorkflowEngineApplication root

The Spring Boot entry point. Running its main method starts the embedded server and wires every @Service, @Repository, and @RestController together.

MiniWorkflowEngineApplicationTests test

A single smoke test confirming the Spring application context loads without error. Not a test of workflow behavior.

06 Known limitations

A work in progress. This list can drift ahead of the actual code — for example, the controller already accepts X-Caller-Role and exposes GET /events, which doesn't by itself mean permissions or event delivery are finished. Verify each row against the current source before trusting it.

GapWhy it mattersA simple fix
No real authentication X-Owner-Id is self-declared, not verified. It isolates integrators' data from each other, but is not security against a malicious caller. Verify a token or API key, then derive the owner ID from it — never trust a caller-supplied header directly. Essential before any real deployment.
No permissions / roles Any caller with a valid owner ID can execute any action on any of that owner's instances. Have the integrating app pass verified user/role information through a trusted integration, and check it against the transition's required role.
Guards exist, but are basic Transitions can be blocked on data — but only with one flat comparison, not compound conditions. Keep the guard set small and explicit (score >= 70, documentsComplete == true). Add compound conditions only once a real workflow needs them.
No hooks / webhook delivery A TransitionEvent is recorded on every transition, but nothing ever reads it and sends a notification. Add a small dispatcher that polls undispatched events and calls a registered webhook URL, then flips dispatched.
Frontend is not data-driven A demo page that hardcodes one workflow's shape can't be pointed at a different workflow. Fetch the definition from GET /workflows/{id} and render whatever states and actions it returns.
No update / delete endpoints A saved workflow definition can be created and read, but not modified or removed. Add versioning first — new instances use the newest version, running instances keep the version they started on. Add archiving after that.

07 What "works for anything" should mean, and the fix order

A reusable engine should work for any process that can be represented as states and actions — without needing a Java code change to define a recruiter approval flow instead of a leave request flow. It doesn't need every feature at once: a full user system, notification service, form builder, and scripting language bolted on together makes the engine harder to understand, not more useful.

The core contract stays small on purpose:

Define a workflow → create an instance → execute an allowed action
                       → read its current state, data, and history

Capabilities get added around that core, in this order:

  1. Secure ownership

    So one integration can never impersonate another. This is the one item that blocks real use — everything else is quality-of-life until this is done.

  2. Verified actor and role checks

    For actions that require a specific person or role, not just a self-declared header.

  3. Reliable events

    So an integrating application can actually react to a state change, not just query it after the fact.

  4. Definition versions

    So workflows can evolve without breaking instances that are already mid-flow on an older version.

  5. Richer conditions

    Only once a concrete use case actually needs more than a single comparison per transition.

Generic does not mean the engine knows every business rule. GIU Nexus decides what "recruiter approved" means and what happens afterward. The engine's job stays fixed: reliably answer "can this instance take this action now, and what state does that put it in?" Fixing the gaps above helps — but authentication and trustworthy permissions are the only ones required before anything else can be called real use.

08 Applying this to any other process

Nothing below requires a code change — only a different POST /workflows body. The same six files that handle "Job Application" handle these too.

Leave requests
SUBMITTED → MANAGER_REVIEW → HR_REVIEW → APPROVED

A guard on the HR_REVIEW → APPROVED transition could check daysRequested <= 20 before allowing it.

Support tickets
OPEN → IN_PROGRESS → WAITING_ON_CUSTOMER → RESOLVED

A required role of agent on the transitions out of OPEN keeps customers from self-closing tickets.

Order fulfillment
PENDING → PAID → SHIPPED → DELIVERED

The same shape used in this project's own CreateWorkflowRequest example — no guard or role needed at all.

Content moderation
SUBMITTED → UNDER_REVIEW → PUBLISHED / REJECTED

Two transitions can share the same fromState and action name if their guards differ — the engine picks the first whose guard matches.

The pattern to copy each time: define the states and transitions as JSON, decide which transitions need a guard or a required role, and let the existing controller, service, and repository layers do the rest. No new Java class is required unless the process needs a genuinely new capability — like the webhook dispatcher in Known limitations.

09 Questions asked along the way

The exchanges that shaped the explanations above, kept as a record of what was asked and how the answer was corrected.

Q How does the engine know which states to add? Isn't that something it should figure out?
Answered above, in "The core idea"

It doesn't figure anything out. Someone defines the workflow first — as a recruiter approval example: states PENDING → LEVEL_1_APPROVED → LEVEL_2_APPROVED → APPROVED, actions approve_1, approve_2, approve_3. That definition arrives as JSON at the workflow creation endpoint. The backend validates and saves it, then creates one instance per recruiter. The engine never invents a step on its own.

Q Why use an engine instead of just writing state logic per process?
Answered above, in "Why use an engine at all"

Because job applications, recruiter approvals, leave requests, and support tickets all ask the same four questions — current state, allowed next action, who can perform it, what happened before. Writing separate state-changing code for each process duplicates that logic four times. Defining each as data and letting one engine manage progression avoids that.

Q Why do those limitations exist, how can they be fixed, and would fixing them even help?
Answered above, in "Known limitations" and "Fix order"

They exist because the engine currently implements the core state machine — define, instantiate, transition — while the surrounding trust and integration layer is still incomplete. Fixing them helps, but not equally: authentication and verified permissions are prerequisites for any real deployment. A generic frontend and richer guard conditions are valuable but can wait until a concrete workflow actually needs them. The important distinction: the fixes make the engine trustworthy and reactive, they don't make it need to understand any more business logic than it already does.

Q I need this engine to work at anything and to be simple — is that realistic?
Answered above, in "What 'works for anything' should mean"

Yes, if "works for anything" is scoped correctly: any process representable as states and actions, defined as data, with no Java change required per process. It should not mean the engine absorbs every possible feature — a full user system, a notification service, a form builder, and a scripting language all at once make it harder to reason about, not more capable. The fix: keep the core contract to define → instantiate → execute → read, and add ownership security, verified roles, events, and versioning around it in that order, only when a real need appears.

Q Do I just start reading all the code, or is there a path?
Answered above, in "The reading path"

A path, not a top-to-bottom read. Follow one request through the whole stack at a time: how a workflow is defined, how an instance runs, how guards and roles restrict a transition, and how history and events get recorded. Each phase above lists the exact files in the order they hand off to each other.

Q Can you describe every source file, one line each?
Answered above, folded into the four reading-path phases

Every file from config, controller, dto, model, repository, and service is covered — grouped by which phase of the request lifecycle it belongs to, rather than as one flat alphabetical list, since that's the order that actually explains why each file exists.

10 A separate project: the Read Aloud Engine

Every read-aloud button on this page and on the source listing is powered by a second, fully independent project — not a feature bolted onto the workflow engine's own code.

This is not part of the workflow engine. It lives in its own folder, read-aloud-engine/, sitting beside mini-workflow-engine/ rather than inside it. It has no imports, no references, and no shared files with the Java project. It doesn't know what a workflow, a state, or a transition is — it only knows how to speak a list of text chunks out loud. The two projects are documented together on this page purely for convenience, side by side, not because they depend on each other.

What it does

It's a small JavaScript library that wraps the browser's built-in speech synthesis (the Web Speech API) so any page can offer a "read this aloud" button. Give it a list of chunks — paragraphs, sentences, lines of code, list items, anything — and it speaks them one at a time, highlighting and auto-scrolling to whichever one is currently playing.

FileRole
read-aloud-engine.jsThe core engine. No DOM opinions, no CSS, no dependencies — just play, pause, stop, and voice selection over a list of chunks.
read-aloud-voice-picker.jsAn optional dropdown UI for choosing a voice, built on top of the core engine. A page that wants its own voice-picker design never has to load this file.
read-aloud-engine.cssAn optional, neutral default stylesheet. Entirely skippable if a page wants to style the active-chunk highlight itself.
demo/index.htmlA plain page with nothing but paragraphs, proving the engine works on any content, not just code.

How this page uses it

Both this documentation page and the full source listing load the same two engine files as an ordinary external script — the same way a completely unrelated website would. Neither page's own code contains any speech logic; they only call the engine's public functions:

const engine = ReadAloudEngine.create();
engine.speak(chunks, { onChunkStart, onChunkEnd, onDone });
engine.stop();

On the source listing, a "chunk" is one line of code. On this page, a "chunk" is one paragraph or list item inside a section. The engine doesn't distinguish between the two — that mapping is entirely up to the page using it.

Voice selection

The engine ranks whatever voices the visitor's own browser reports, biased toward known natural-sounding female voices (for example Google's, Microsoft's Aria/Jenny, or macOS's Samantha/Victoria), and picks the best match automatically. Exactly which voices exist is entirely up to the visitor's operating system and browser — this library cannot add voices that aren't already installed. Double-clicking any read-aloud button opens a picker to override the automatic choice, and that choice is remembered for next time.

Using it on another website

Nothing about it assumes this project's markup, styling, or content. To add it elsewhere:

  1. Copy read-aloud-engine.js (and optionally the voice picker and CSS) into the target site — no build step or package manager required.
  2. Decide what counts as a "chunk" for that page's content: a paragraph, a sentence, a table row, a line of code.
  3. Wire a button to call engine.speak(chunks, callbacks) with those chunks.
  4. Optionally use the onChunkStart / onChunkEnd callbacks to highlight the active chunk and scroll it into view.

The full API — every method, every option, and the browser-support caveats — is documented in the engine's own README.md, which travels with the project's files.

11 A third project: Arthur, the page chatbot

The chat bubble in the bottom-right corner of this page is also its own standalone project, not a feature of the workflow engine's code.

Arthur is not part of the workflow engine, and not part of the Read Aloud Engine either. It lives in its own folder, arthur-chat-engine/, beside both other projects. It has no knowledge of workflows, states, or transitions built into it — it only knows how to index whatever text a page gives it and find the most relevant passage for a question.

How Arthur actually answers

Arthur is a local keyword-search engine with a bounded personality, not a large language model, and runs entirely in the visitor's browser with no server, no API key, and no web access. When this page loads, it feeds Arthur every heading and paragraph on the page. When someone asks a question, Arthur first checks whether it's small talk or a question about himself; if not, he checks whether it's clearly off-topic; only then does he score every indexed passage by how many meaningful words — including synonyms — it shares with the question, favoring headings, and return the best match.

That has real limits, stated plainly: Arthur cannot generate a new sentence beyond his small-talk replies, cannot reason across passages the way a real conversational model can, cannot browse the web, and can only answer document questions this page actually addresses somewhere in its text. Ask him something the page never covers and he says so, rather than guessing — and ask him something clearly unrelated to the document, and he declines in character instead of trying to answer from general knowledge he doesn't actually have.

Small talk and staying on topic

Say hi, and Arthur says hi back. Ask "who are you" or "what can you do," and he answers honestly, in his own voice, without pretending to be a general-purpose assistant. Ask him something with no connection to this document at all — general trivia, current events, or anything on a small built-in list of clearly out-of-scope subjects — and he declines, by design:

You: "hi"
Arthur: "Hey! I'm Arthur. Ask me anything about this workflow engine…"

You: "tell me about nuclear weapons"
Arthur: "I'm built specifically to answer questions about this workflow engine and about myself — I won't get into that."

This boundary is implemented as two small, inspectable pieces in arthur.js: a handful of regular expressions that recognize greetings, thanks, and questions about Arthur himself before any document search runs, and a short blocklist of clearly unrelated subjects (weapons, politics, celebrities, recipes, and the like) checked before falling back to search. A question that shares no vocabulary with the document at all — but isn't on that blocklist — still gets an honest "I couldn't find anything about that" rather than a refusal, since Arthur isn't trying to police every possible topic, only the ones a visitor might plausibly test him with.

Understanding abbreviations and slang

Before anything else runs, Arthur expands a fixed table of shorthand people actually type: "u" becomes "you", "r" becomes "are", "ngl" becomes "not gonna lie", "wsp" becomes "what's up", "hru" becomes "how are you", and so on. So "who r u" is understood exactly like "who are you", and a question like "ngl what do guards do" still finds the right passage. This is a lookup table, not language understanding — it only recognizes the specific shorthand it's been given.

Talking to Arthur in other languages

Arthur can also recognize and reply to greetings, thanks, farewells, and "who are you" in Spanish, French, German, Arabic, Hindi, and Chinese, each with hand-written replies in that language:

You: "hola"
Arthur: "¡Hola! Soy Arthur. Pregúntame lo que quieras sobre this workflow engine."

You: "qui es-tu"
Arthur: "Je suis Arthur, un assistant local pour this workflow engine…"
This is small talk, not translation. Arthur has no language model and cannot translate this documentation's actual content. A Spanish or French greeting gets a warm reply in that language, but a real question about how guards or transitions work still gets answered from this page's English text — Arthur says so honestly rather than pretending to fully understand every language.

Copy, read aloud, and "show me in the page"

Every answer Arthur gives has a Copy button, the same pattern used throughout this documentation and the source listing. If the separate Read Aloud Engine is also loaded on the page — which it is here — each answer also gets a Read aloud button, so an answer can be heard instead of read. This integration is optional and detected at runtime: Arthur works completely on its own if that other project isn't present. Answers also include a "Show me in the page" link that scrolls to and briefly highlights the passage the answer came from, so a reader can verify Arthur's answer against the source.

Using it on another website

Nothing about Arthur assumes this project's subject matter. To add it elsewhere:

  1. Copy arthur.js (and optionally the widget files) into the target site.
  2. Call arthur.index(...) with the page's own headings and paragraphs once it has loaded.
  3. Mount the included chat widget, or call arthur.ask(question) from a custom interface.

The full API, including the confidence score and the "why keyword search, not a real AI" reasoning behind Arthur's design, is documented in its own README.md, which travels with the project's files.
